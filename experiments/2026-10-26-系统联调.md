# 系统联调记录 —— 端到端验证

**日期**：2026-10-26
**主题**：8.1 震动状态监测器 · 端到端联调（真实振动 → 边缘判定 → MQTT → 仪表板 → 报警）

---

## 1. 验证目标

确认完整数据链路可用，且**判定在边缘完成**（ESP32 自学习基线并判定状态），
服务端仅负责传输、存储与展示。

```
MPU6050 → ESP32（采样 + FFT + 带限 RMS + 基线自学习 + 迟滞判定）
        → Wi-Fi → MQTT → Node-RED（aedes broker）
        → 仪表板（实时/趋势） + SQLite（历史） + 日志文件
```

## 2. 环境

| 项目 | 值 |
|---|---|
| 节点 | ESP32-WROOM-32，COM8，固件 `09_mqtt_telemetry` |
| 传感器 | MPU6050（I²C 0x68），固定于风扇外框 |
| 被测对象 | YD9225HSL 5 V 风扇，实测转频 34.2~35.2 Hz（约 2050~2110 RPM） |
| 网络 | 手机热点 `XiXiaomi`（2.4 GHz，WPA2） |
| 笔记本 | 10.77.48.14（热点 DHCP） |
| 服务端 | Node-RED 5.0.8，aedes broker 1883，仪表板 1880/ui |
| 数据库 | SQLite `vibration.db`，表 `readings` |

## 3. 固件工作流程

1. 连接 Wi-Fi、连接 MQTT broker
2. **基线自学习**：连续采集 15 帧（每帧 1024 点 @ 1 kSPS），
   计算带内 RMS 的均值 μ 与标准差 σ
3. 阈值：注意 = μ + 3σ，报警 = μ + 6σ
   （σ 下限保护：不小于 0.15 μ，避免基线过稳导致阈值过紧）
4. 循环：每 2 s 测量一帧并上报；判定采用迟滞
   （升级需连续 3 帧确认，降级需连续 5 帧确认）

上报主题：`smartcampus/vib/{node_id}/state`

```json
{"node":"esp32-01","seq":105,"rms":0.0598,"peak":0.0453,
 "fpeak":35.2,"tchip":24.4,"state":"normal",
 "warn":0.0763,"alarm":0.1000}
```

## 4. 自学习结果

```
[ 1/15] RMS = 0.0508 g
[ 2/15] RMS = 0.0492 g
...
[15/15] RMS = 0.0558 g

基线: mu = 0.0526 g,  sigma = 0.0079 g
阈值: 注意 = 0.0763 g,  报警 = 0.1000 g
```

15 帧 RMS 落在 0.0492~0.0569 g，一致性良好（σ/μ = 15 %）。

## 6. 发现与说明

1. **阈值必须由基线自学习得到**。此前用固定的 0.030/0.060 g 作占位值，
   与实际噪声水平不符；自学习得到的 0.0763/0.1000 g 与实测数据吻合。

2. **同一装置在不同次装配下绝对幅值会漂移**（基准 RMS 曾出现 0.0516 与 0.1123 两种量级），
   因此每次装配后必须重新自学习基线。固件支持串口发送 `r` 重新学习。

3. **仪表盘量程需按工况设置**。RMS 在正常与严重不平衡之间跨越约 10~60 倍，
   线性量程无法兼顾；最终取 0~0.5 g（正常工况可读），
   严重不平衡时指针顶到上限并伴随整圈变红，视觉上仍能明确表达"越限"。

4. **服务端不再重复判定**。状态与阈值均由 ESP32 上报，
   Node-RED 仅做映射（英文状态 → 中文等级与建议）、存储与展示，
   符合"边缘处理而非原始转发"的设计要求。

## 6. 调试记录：历史曲线空白问题

联调过程中"历史查询"页始终空白，排查过程记录如下，可作为同类问题的参考。

### 6.1 现象

- 数据库有 600+ 条记录，直接查库能返回 200 条
- 仪表板"历史查询"页的图表框架正常，但**没有曲线**
- Node-RED 每 30 秒输出一条警告：`[ui_chart:数据库历史曲线] Bad data inject`

### 6.2 排查与修复（三个独立问题叠加）

**问题一：数据格式不符合节点要求**

查看 `node_modules/node-red-dashboard/nodes/ui_chart.js:74` 可知，批量注入时
payload 必须是：

```js
[{ series: ['名称'], data: [[x, y], ...] }]
```

而原实现发送的是 `[{x: 时间, y: 值}]`，缺少 `series` 与 `data` 字段，
被节点判定为非法并丢弃，因此每 30 秒报一次 `Bad data inject`。

修复：改为该节点要求的 `{series, data}` 结构。

**问题二：批量格式能通过校验但画不出线**

改格式后警告消失，但图表仍无曲线。逐条比对发现，该版本 UI 对
"单点 + `msg.timestamp`" 与"批量数组"走的是两条不同代码路径，
其中单点路径（实时趋势图所用）经验证可靠。

修复：改为先发 `{payload: []}` 清空，再逐条发送
`{ payload: <数值>, timestamp: <毫秒时间戳> }`。

**问题三（根本原因）：`removeOlder` 设为 0 导致所有点被立即丢弃**

检查节点配置发现历史图的 `removeOlder` 为 `"0"`、`removeOlderUnit` 为 `"3600"`。
原意是"永不删除历史点"，但该参数语义是"**只保留最近 N 小时**"，
`0` 意味着保留窗口为 0 —— 客户端每收到一个点就立刻判定为过期并丢弃。

**实时趋势图的同一参数是 `60`（60 分钟），所以一直正常**；
两者只差这一个数字，行为却完全不同。

修复：改为 `removeOlder = "24"`、`removeOlderUnit = "3600"`（保留 24 小时）。

### 6.3 修复后的验证

历史页正确显示 16:28–16:38 的完整曲线：

| 时段 | RMS | 说明 |
|---|---|---|
| 16:28–16:30 | ≈ 0 | 风扇停转 |
| 16:31:30–16:33:00 | **0.6 ~ 0.8 g** | 0.35 g 配重的报警段 |
| 16:33 之后 | ≈ 0 | 拆配重、停机 |

### 6.4 经验

1. 第三方节点的**配置语义不能靠猜**，`removeOlder = 0` 这种"看起来像关闭"
   的值往往是"窗口为 0"，恰好是相反的效果。
2. 排查时**先对比同项目中"能正常工作"的同类节点**，差异往往一目了然
   —— 本次的突破口正是实时趋势图的 `removeOlder = 60`。
3. 读**源码**比读文档快：`Bad data inject` 这个提示在源码里只有一处，
   定位后立即看到它对 payload 结构的要求。
